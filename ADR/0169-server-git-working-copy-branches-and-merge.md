# ADR 0169 — Cartella di lavoro Git sul server, branch e unioni con conflitti curati dall'autopilot

- Stato: **implementato nel sorgente** (frontend e motore dalla 0.33.0, server da sorgente); non è un'installazione server completa.
- Data: 2026-11-19.
- Integra ADR 0005–0009 (GitHub, outbox, lease, conflitti), 0083–0088 (ACK, recupero), 0125 (CAS), 0165–0166 (salvataggio continuo, lease) e 0167–0168 (server personale e motore condiviso).
- [Guida](../docs/personal-server-git.md) · [F04](../features/F04-server-git-branches-merge.md).

## Richiesta

Il server deve gestire GitHub lavorando davvero con `git`: clonare in una cartella di lavoro, fare il pull, lavorare di default su `main` ma poterlo cambiare, creare branch da altri branch, rifare i merge e usare l'autopilot per curare i conflitti. Se l'autore lavora da un client e rimanda il libro al server, il server legge prima il repository.

## Decisioni

1. **Git è un trasporto, non una seconda logica.** Il motore parla con GitHub solo tramite le richieste della Git Data API. `HostRuntime.gitHub` (opzionale) permette a un host di rispondere a quelle richieste da sé. Il server lo implementa con il **binario `git`** (`src/server/src/git.ts`): una copia di lavoro per repository (`<dati>/git/<owner>__<repo>`), `git fetch` a ogni lettura di un ref, oggetti creati con indice temporaneo, `git push <sha>:refs/heads/<ramo>` **senza mai forzare**. Marker di operazione, ACK esatto, recupero di un esito incerto, autorità e lease restano quelli del motore: stesso codice, stesse prove. Il browser non cambia (HTTPS verso api.github.com). Senza `git` ≥ 2.32 il server ricade sull'API REST e lo dice nel pannello amministrativo.
2. **La verità resta il libro, non i file.** La cartella di lavoro è derivata dal ramo dopo ogni push: modifiche manuali al suo interno vengono scartate. Il libro nel contenitore del server è lo stato operativo; il Markdown è proiezione, come oggi.
3. **Il ramo del libro è `remote.branch`** (default `main`). Cambiare ramo sostituisce il testo del libro con quello del ramo e perciò richiede che il libro sia salvato (mai si perde testo); creare un ramo dal corrente e passarvi conserva le modifiche non salvate, come `git checkout -b`.
4. **Pull prima di lavorare.** Prima di `start`, prima di «Salva su GitHub dal server», alla fine di ogni corsa e con il comando `git_pull`, il server confronta la testa del ramo con l'ultima versione confermata. Nessuna modifica locale e testa discendente: fast-forward. Altrimenti **unione a tre vie**. Non avviene durante una corsa: un autosync che trova il ramo cambiato resta bloccato finché non c'è un pull.
5. **L'unione è a livello di libro, non di file.** Un merge testuale di `project.json` non ha senso. Si usa l'antenato comune (`compare`/merge-base), il confronto per unità già esistente (`compareBookVersions`: campi, capitoli, scene, memoria, stato, timeline, più le schede narrative) e: ciò che cambia da un solo lato si prende da solo; due modifiche della **stessa scena in righe non sovrapposte** si uniscono per righe (diff a tre vie limitato, righe adiacenti = conflitto); il resto è un conflitto. Senza antenato nessuna differenza è attribuibile a un lato: tutto è conflitto. Il risultato è un **commit di merge con due genitori**, pubblicato con le stesse regole di ogni push (`force:false`, ACK). I capitoli toccati sono riaperti e perdono il congelamento (come ogni risoluzione da GitHub).
6. **I conflitti sono uno stato durevole** (`BookProject.mergeSession`, solo operativo: mai nel Markdown/GitHub, rimosso all'importazione, blocca la pubblicazione). Il libro non può cambiare mentre l'unione attende (impronta narrativa verificata), `start` è rifiutato salvo in modalità autopilot, e nulla esce prima che ogni conflitto abbia una decisione. La conclusione rilegge i rami: se si sono mossi, si annulla e si ripete.
7. **L'autopilot cura le scene modificate in entrambi i branch.** Con il consenso esplicito di quella unione (`consentAi`, per le scene e il canone con i segreti) il runner esegue un task `merge` per ogni scena in conflitto (route `merge`, scene come dati non attendibili, base comune nel prompt). La proposta è **bozza** in un capitolo riaperto: non è canone finché la revisione editoriale normale non la congela; non resta una conferma nel Lettore. Gli altri conflitti (campi, schede, memoria, scene presenti in un solo ramo) restano all'autore e l'autopilot si ferma spiegandolo. Quando tutto è deciso il server pubblica l'unione e lascia il libro in pausa.
8. **Sicurezza di `git`.** PAT solo nell'ambiente del processo figlio (`http.https://github.com/.extraheader`), mai in argv, URL, `.git/config` o errori. Host fisso `https://github.com/<owner>/<repo>.git` da nomi validati; ambiente costruito da zero (HOME privata, nessun config di sistema o utente, niente prompt, nessun credential helper); protocolli ristretti, redirect disattivati, hook disattivati, `fsckObjects`, symlink disattivati, percorsi validati prima di scrivere un albero, uscita e tempo limitati. I rami `bookwriter-lock/*` del lease non sono elencati né modificabili.

## Conseguenze e limiti

- Il lease e le letture di metadati restano REST; la fusione di due rami dello stesso libro usa gli stessi lock di writer e outbox del resto.
- Il limite di 12 MiB per push resta (misura UTF-16 del motore). I comandi HTTP accettano 64 KiB: una proposta di testo scritta dall'autore è breve; la UI offre «tieni/prendi».
- Fuori da questa tranche: **adottare dal server un libro già su GitHub** e il **ritorno al locale** (servono il protocollo di autorità nei due sensi), rebase, cherry-pick, eliminare rami, tag, pull request. Le schede narrative si uniscono come un'unica unità; dati operativi (consensi, budget, instradamenti) restano quelli del ramo che riceve.
- Provato con repository locali e GitHub simulato; non con GitHub reale, 401/403/branch protetti reali, Windows o proxy (`HTTPS_PROXY` non è inoltrato).
